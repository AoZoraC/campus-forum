# 开发环境踩坑记录

> 这份文档记录的是**真实踩过的坑**，不是从教程抄的。
> 它们的共同特点：报错信息完全看不出原因，而且网上搜不到。
> 以后再遇到类似症状，先翻这里。

---

## 1. pnpm 12 在这个环境里根本跑不起来

**现象**

```
Error: ERR_PNPM_CLI_DLX_CACHE
Failed to prepare the dlx cache directory C:\Users\...\AppData\Local\pnpm-cache\dlx\...
拒绝访问。 (os error 5)
```

换成 `--state-dir` 参数后，又变成：

```
Error: ERR_PNPM_STORE_DIR_OPEN_OPERATION_LOCK
Failed to open the store operation lock at "pnpm-store-operation-locks": 拒绝访问。
```

**原因**

- pnpm 从 v10 起，除 `registry` 和认证之外的配置**全部从 `.npmrc` 搬到了 `pnpm-workspace.yaml`**。写在 `.npmrc` 里的 `store-dir`、`cache-dir` 会被静默忽略（`pnpm config get` 返回 `undefined`）。
- 就算把路径配对了，pnpm 12 是 Rust 重写的，启动时要开一个「操作锁」文件，某些受限环境里这个操作会被拒绝。

**解法**

**换用 npm。** 它是 Node 自带的，与系统兼容性最好 —— 对新项目来说，pnpm 省下的那点磁盘和几十毫秒，完全不值得为它折腾半天。

如果坚持要用 pnpm，正确写法是在项目根建 `pnpm-workspace.yaml`：

```yaml
storeDir: D:/path/to/.pnpm-store
cacheDir: D:/path/to/.pnpm-cache
```

（注意是驼峰命名，和 `.npmrc` 里的 `store-dir` 不一样。）

## 2. 缓存目录默认写在系统盘，受限环境会失败

**现象**

```
npm error code EPERM
npm error path C:\Users\...\AppData\Local\npm-cache\_cacache\tmp\***
```

**原因**

npm 默认把下载缓存放在 `C:\Users\<你>\AppData\Local\npm-cache`。如果工具运行在受限沙箱里，写系统目录会被拒绝。

**解法**

把缓存指到项目目录内：

```ini
# .npmrc
cache=D:\tool\Code\Git\.npm-cache
```

**注意一个隐蔽的坑**：项目级 `.npmrc` **只在项目根目录生效**。如果在子目录里执行 npm 命令（比如在一个空的 `_scaffold/` 里跑 `create-next-app`），它读不到这个配置，又会退回系统目录。这时要用环境变量强制指定：

```powershell
$env:npm_config_cache = "D:\tool\Code\Git\.npm-cache"
```

环境变量的优先级**高于所有配置文件**。

## 3. create-next-app 会往 APPDATA 写偏好设置

**现象**

```
Error: EPERM: operation not permitted, mkdir
'C:\Users\...\AppData\Roaming\create-next-app-nodejs\Config'
```

**原因**

`create-next-app` 用了一个叫 `conf` 的库来记住你的选择偏好，它固定往 `%APPDATA%` 写。

**解法**

临时把 `APPDATA` 指到项目内：

```powershell
$env:APPDATA = "D:\tool\Code\Git\.appdata"
```

## 4. npm 的 `latest` 标签可能指向预发布版

**现象**

装了 `prisma`，结果得到 `8.0.0-rc.22` —— 一个 Release Candidate。

跑 `npx prisma validate` 直接报：

```
CLI.UNKNOWN_COMMAND: No command registered for 'validate'
```

**原因**

Prisma 8 把 CLI 彻底重构了，变成了一套「开发平台」CLI（`auth` / `project` / `deploy` / `contract` …），**传统的 `generate`、`migrate dev`、`validate`、`studio` 全不见了**。而官方把 `latest` 标签指给了 RC 版本。

**解法**

**装依赖时永远看一眼版本号，不要盲信 `latest`。** 需要稳定版就锁版本：

```powershell
npm install prisma@7.10.0 --save-dev
```

查版本标签：

```powershell
npm view prisma dist-tags --json
# { "latest": "8.0.0-rc.22", "prev": "7.10.0", ... }
#                              ↑ 真正的稳定版在这里
```

## 5. Prisma 7 把连接地址搬出了 schema 文件

**现象**

```
error: The datasource property `url` is no longer supported in schema files.
error: The datasource property `directUrl` is no longer supported in schema files.
  → Move connection URLs to `prisma.config.ts`
```

**原因**

Prisma 7 的架构变化：

| | Prisma 6 及以前 | Prisma 7 |
|---|---|---|
| 连接地址 | `schema.prisma` 里的 `url` / `directUrl` | 独立的 `prisma.config.ts`，只剩一个 `url` |
| CLI 用哪个地址 | `url` 给运行时、`directUrl` 给迁移 | **`url` 就是给迁移用的** |
| generator | `prisma-client-js`，无 output | `prisma-client`，**必须写 `output`** |
| 客户端来源 | `@prisma/client` | 你配置的生成目录 |
| 环境变量 | 自动读 `.env` | **必须装 `dotenv` 并 import** |

**解法**

按新写法配置。另外官方文档特意提醒了一个坑：`env()` 助手在变量缺失时会抛错，而它是在**加载配置文件时**执行的 —— 也就是说哪怕你只是跑 `prisma generate`（根本不需要数据库），只要 `.env` 没配好也会失败。

所以 `prisma.config.ts` 里推荐写：

```ts
datasource: {
  url: process.env.DIRECT_URL ?? "",   // 而不是 env("DIRECT_URL")
}
```

## 6. `P1001 Can't reach database server` 不一定真的是「连不上」

**现象**

```
Error: P1001: Can't reach database server at `xxx.pooler.supabase.com:5432`
```

但同一台机器上，用 `pg` 驱动连同一个地址**完全正常**。

**原因**

- 可能是**太慢**而不是不通。实测直连 Supabase 耗时 **3.4 秒**，已经逼近 Prisma 的默认连接超时，于是被判定成「连不上」。
- 也可能是**那条通道本身不被支持**。Supabase 的 Session pooler（`pooler.supabase.com:5432`）就是 Prisma 迁移引擎走不通、而普通驱动能走通的一条路。

**解法**

1. 先做**连通性实测**，别猜 —— 用 TCP 连接 + `pg` 驱动各测一次，看是「不通」还是「慢」。
2. 给连接串加超时余量：
   ```
   postgresql://...?connect_timeout=30
   ```
3. **不要凭想象改配置**。当时我担心「国内网络只有 IPv4，连不上 Supabase 的 IPv6 直连」，于是把地址改成了连接池 —— 结果实测发现 IPv6 本来就是通的，改过去反而走进了迁移引擎不支持的那条路。**预防性优化必须先验证假设。**

## 7. Supabase 的两个地址、三个端口

这是最容易搞混的地方：

| 用途 | 地址特征 | 端口 |
|---|---|---|
| 网站运行时（高并发） | `xxx.pooler.supabase.com` | **6543**（Transaction pooler） |
| 迁移建表（需要完整会话） | `db.xxx.supabase.co` | **5432**（直连） |
| 直连的 IPv4 替代品 | `xxx.pooler.supabase.com` | 5432（Session pooler） |

- 用户名格式不同：**连接池要带项目引用**（`postgres.项目名`），**直连不带**（就是 `postgres`）。
- 地址里的 `[YOUR-PASSWORD]` 占位符**必须手动替换**，密码里的特殊字符（`@ # ? &`）还要做百分号转义。
- 面板改版频繁，**地址入口在右上角的 `Connect` 按钮里**，不在「设置」页。也可以直接用参数直达：`/dashboard/project/<项目ID>?showConnect=true`。
- 免费项目**连续 7 天无活动会被暂停**，需要去面板点恢复。

## 8. Node.js 已经内置了很多「必备工具」

**现象**

`tsx`（常用来运行 TypeScript 脚本的工具）失败：

```
Error: spawn EPERM
    at ensureServiceIsRunning (esbuild/lib/main.js)
```

因为它的底层 `esbuild` 要 spawn 一个服务进程。

**解法**

**Node 22.6+ 可以原生运行 `.ts` 文件**（类型剥离），所以直接：

```powershell
node scripts/xxx.ts
```

这条规律值得记住：Node 这几年把很多东西收进了内核 —— TypeScript 支持、测试运行器、`--env-file`、SQLite（`node:sqlite`）。**当你为了某个语法装了一堆工具时，先查查运行环境本身是不是已经支持了。**

## 9. 沙箱环境里根本跑不了 Next.js 开发服务器

**现象**

```
Error: spawn EPERM
    at fork (node:internal/child_process:174:10)
    at next-dev.js:393:45  →  startServer
```

**原因**

Next.js 的开发服务器要用 `fork()` 启动子进程，而 `fork` 需要 IPC 通道（命名管道）。受限沙箱禁止进程创建命名管道。

**解法**

这类操作只能由**人在正常终端里执行**。由此形成分工：

- **AI 做**：写代码、读官方文档、类型检查、静态验证、查资料
- **人做**：跑 dev server、执行需要 spawn 的命令、涉及账号和权限的操作

> 这不是缺陷，而是**安全边界该有的样子**。理解这条边界在哪，比试图绕过它更有价值。

## 10. `prisma migrate dev` 会卡住 —— 影子数据库的坑

**现象**

`npx prisma migrate dev --name xxx` 打印完 `Datasource "db": ...` 之后就**一直卡着不动**，不报错，也不结束。

**原因**

`migrate dev` 不只是执行 SQL，它还要**创建一个临时的「影子数据库」**，用来对比检测迁移是否漂移。

而 Supabase 免费版的 `postgres` 用户**通常没有创建数据库的权限** —— 于是这个操作就一直等下去。

**解法**

用 `deploy` 代替 `dev`，它只应用已有迁移，不碰影子数据库：

```powershell
npx prisma migrate deploy
```

**更底层的解法**（当连 `deploy` 都跑不起来时）：

迁移的本质其实只有两件事：

1. 执行 `migration.sql` 里的 SQL
2. 往 `_prisma_migrations` 表插一条记录（`checksum` 字段是**该 SQL 文件的 sha256**，这一点已实测验证）

所以**任何一个能连数据库的客户端都能完成迁移** —— 哪怕是一段 20 行的 Node 脚本。做法是：

- 在 `prisma/migrations/` 下建目录，命名格式为 `<时间戳>_<名字>`（时间戳要晚于已有迁移）
- 里面放 `migration.sql`，格式照 Prisma 生成的样子写
- 用 `pg` 执行它，再把记录插进 `_prisma_migrations`

> 这条经验的意义不在于「绕过工具」，而在于**看穿工具的包装**。工具的价值是帮你兜住 90% 的边界情况；当它挡住你时，知道它底下在做什么，你就有第二条路。
